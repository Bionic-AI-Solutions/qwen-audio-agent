# Data Models and Persistence

> Generated by SKAD `document-project` step 4 (deep scan) on 2026-09-05.
> Covers `requires_data_models` for parts `server`, `web`, and `mobile`.
> Source: `server/src/core/`, `server/src/task/`, `server/src/conversation/`,
> `server/src/access/`, `server/src/domain/`, `server/src/agent/`, `shared/`.

## Headline: there is no database

**No relational database, no ORM, no migration framework, no document store.** The scan found:

- Zero files matching `migrations/`, `prisma/`, `alembic/`, `knex/`, `*.sql`
- Zero dependencies on `pg`, `mysql2`, `sqlite3`, `better-sqlite3`, `mongodb`, `redis`, `level`
- The only file with "migration" in its name is `desktop/src/config-migration.mjs`, which migrates a
  **settings file**, not a schema

All durable state is **versioned JSON snapshots on the local filesystem**, written atomically. The
web and mobile parts hold **no persistent data models of their own** beyond the mobile pairing
profile (see [`frontend-architecture-mobile.md`](./frontend-architecture-mobile.md)); everything
else is fetched from the Gateway per session.

This follows from the product shape: the Gateway is a local, single-user process that keeps an
agent conversation alive. Adding a database would change the deployment story, not just the storage
layer.

## The two persistence base classes

Both live in `server/src/core/` and both encode the same four policies. **New durable state should
subclass or instantiate one of these rather than calling `fs` directly** — the policies below are
the reason they exist.

### Shared policies

| Policy | Mechanism |
| --- | --- |
| **Atomic write** | Write to `<path>.<pid>.tmp`, then `renameSync` over the target. A crash mid-write can never leave a half-file |
| **Private mode** | Files written `0o600` — several of them hold credentials |
| **Corruption quarantine** | Invalid JSON, wrong version, or failed validation → rename to `<path>.corrupt-<timestamp>`, warn, and continue with an empty snapshot |
| **Degrade, never crash** | If quarantine itself fails, persistence is disabled to protect the original file and the service keeps running in memory. Diagnostics callbacks are wrapped in `try/catch` so a logging failure cannot prevent startup |

**`ENOENT` is not an error** — a missing file is a first run and yields the fallback value.

### `VersionedJsonStore` (`core/versioned-json-store.mjs`, 99 LOC)

The simpler of the two. Caller-supplied `fallback()` and `validate()`:

```js
store.load({ fallback: () => ({ devices: [] }),
             validate: value => Array.isArray(value.devices) })
store.save(value)   // persists { version, ...value }
store.health()      // { ok, persistenceEnabled, warning }
```

### `JsonSnapshotStore` (`core/json-snapshot-store.mjs`, 177 LOC)

Adds three things over `VersionedJsonStore`:

1. **`requiredKeys`** — declared top-level fields a snapshot must have, checked before use.
2. **mtime + SHA-1 content hash** double detection of external modification. The comment explains
   why both: *NTFS and rapid consecutive writes can land on the same timestamp tick*, so mtime alone
   is not sufficient.
3. **`replaceFileSync`** from `shared/file-transaction-lock.mjs` instead of a bare rename, plus an
   explicit `chmodSync`.

It is **deliberately opaque to the data model** — serialization and deserialization are the
subclass's job; the store only handles getting a JSON blob safely to and from disk.

### The version-bump rule

Stated explicitly in the source comments of both `json-snapshot-store.mjs` and
`preference-candidate-store.mjs`, and worth restating because getting it wrong fails silently:

> **When the shape of persisted data changes, `fileVersion` MUST be incremented.**
> A version mismatch routes the old file to quarantine with a warning. Without the bump, an old file
> is parsed as the new format, every record fails validation, and the snapshot silently becomes
> empty — data loss with no error.

## Persisted collections

Six durable stores exist. Each row is a separate file.

| # | Store | Module | Base | Version | Snapshot shape |
| --- | --- | --- | --- | --- | --- |
| 1 | Tasks | `task/task-store.mjs` | *(bespoke)* | 1 | `{ version, tasks: [...], nextTaskNumber }` |
| 2 | ACP session index | `agent/acp-session-registry.mjs` | `VersionedJsonStore` | 1 | `{ version, coordinators, projects, reconciliations }` |
| 3 | Remote devices | `access/gateway-access.mjs` | `VersionedJsonStore` | 1 | `{ version, devices: [...] }` |
| 4 | Domain library index | `domain/domain-library.mjs` | `JsonSnapshotStore` | `FILE_VERSION` | `{ version, owners: {...} }` |
| 5 | Session digests | `conversation/session-digest.mjs` | `JsonSnapshotStore` | `FILE_VERSION` | `{ version, owners: {...} }` |
| 6 | Preference candidates | `conversation/preference-candidate-store.mjs` | `JsonSnapshotStore` | **2** | `{ version, owners: {[id]: [slot...]}, blocklist: {[id]: [key...]} }` |

### 1. Tasks — `TaskStore` + `TaskRepository`

The only store with its own bespoke implementation, because it needs **deferred writes**.

`TaskStore` adds a `deferredDelayMs = 250` write coalescer (`deferredTimer`, `deferredContent`,
`writeGeneration`, `deferredWrites`) on top of the standard atomic/quarantine behavior. Task state
changes rapidly during a turn; without coalescing, every event would hit the disk.

`TaskRepository` (76 LOC) owns the in-memory `Map` of records and the **durable short-id cursor**:

```
allocateTaskId() → "task_<n>",  1 ≤ n ≤ 99_999, wrapping to 1 at the ceiling,
                   skipping ids already present in `records`
```

The cursor is persisted as `nextTaskNumber` so short ids stay stable and non-colliding across
restarts. `normalizedTaskNumber()` clamps any out-of-range or non-integer stored value back to `1`
rather than throwing — a corrupt cursor degrades to a restart of the numbering, not a crash.
It also reads a legacy `nextJobNumber` key as a fallback, so older files still load.

Recovery policy deliberately stays in `TaskManager`; the repository owns only the record
collection, its persisted projection, and the cursor.

### 3. Remote devices — `GatewayDeviceRegistry`

Records are **filtered on load**: a device missing `id`, `ownerId`, or `tokenHash` is dropped
silently. Tokens are stored as a **hash**, never in plaintext, which is what makes per-device
revocation possible without the Gateway holding the credential.

### 6. Preference candidates — why it must persist

The comment states the design constraint plainly: promotion of a preference requires evidence
**across ≥2 sessions**. A purely in-memory pool resets on restart, so cross-session evidence could
never accumulate and *the promotion mechanism would silently never fire*. Persistence is a
correctness requirement here, not an optimization.

Version 2 replaced v1's free-text trait + counter model with a **slot model** (`field` / `value` /
`confirm`). `MAX_OWNERS = 200`.

### Bounded-growth constants

Every store caps its own growth — there is no external compaction process:

| Constant | Value | Module |
| --- | --- | --- |
| `MAX_TASK_NUMBER` | 99,999 | `task-repository.mjs` |
| `MAX_OWNERS` | 200 | `preference-candidate-store.mjs` |
| `MAX_EDIT_ITEMS` | 20 | `markdown-context-store.mjs` |
| `MAX_ENTRIES_PER_OWNER`, `MAX_FILE_BYTES` | — | `domain-library.mjs` |
| `MAX_SESSIONS_PER_OWNER`, `RETENTION_MS` | — | `session-digest.mjs` |

Session digests are the only store with **time-based retention** (`RETENTION_MS`).

## Markdown as a data model

`conversation/markdown-context-store.mjs` (251 LOC) is the odd one out: its persisted form is
**Markdown text**, not JSON. It backs the `frontend.memory-control` capability
(`GET`/`PATCH /api/memory`).

Notable mechanics:

- `normalizeMarkdown(content)` canonicalizes before comparison, so cosmetic differences do not
  register as edits.
- `digest(value)` produces a revision identifier, and `publicDocument(scope, content, revisionSource)`
  is the client-facing projection — **the storage layout never leaks to clients**.
- `countOccurrences(content, needle)` supports targeted edits: an edit is applied only when its
  anchor text is unambiguous.
- `MAX_EDIT_ITEMS = 20` caps a single edit batch.

## Wire schemas (zod) — validation, not storage

Distinct from persistence: `shared/` defines the **runtime validation** layer for messages crossing
the WebSocket. These are contracts, not tables, and are the published API surface.

### `shared/gateway-client-protocol.mjs` — GCP6 envelopes

A base envelope with two variants and 26 extensions:

```
GatewayClientEnvelopeSchema
├── GatewayServerEnvelopeSchema (extends)
├── GatewaySessionHelloSchema, GatewayClientEventPublishSchema,
│   GatewaySessionOutputVoiceUpdateSchema, GatewayClientActionResultSchema
├── Task ops:  GatewayTaskCreate / TaskGet / TaskList / TaskCancel
└── Other ops: GatewayPermissionRespond, GatewayInputRespond,
               GatewayConversationHistory, GatewaySessionReplay
```

Each request has a paired `…ResultSchema` on the server envelope; the task results share a
`TaskResultBaseSchema`. Server-originated: `GatewaySessionReadySchema`,
`GatewayProtocolErrorSchema`, `GatewayClientActionRequestSchema`.

### `shared/gateway-remote-access.mjs` — pairing

`GatewayUrlSchema` (trimmed, non-empty, transformed by `normalizeGatewayUrl`),
`GatewayEndpointDescriptorSchema`, `GatewayConnectionProfileSchema`, `GatewayInvitationSchema`.

### Server-side message schemas

Catalogued in [`api-contracts-server.md`](./api-contracts-server.md) — `GatewayTaskSchema`,
`GatewayArtifactSchema`, `GatewayCitationSchema`, `GatewayInputPartSchema` (a discriminated union on
`type`), and the rest, with `parseGatewayClientMessage` / `parseGatewayServerMessage` as entry
points.

## Where data lives on disk

Paths are configuration-driven, not hard-coded here. Two relevant rules:

- **The desktop app requires an explicit `configDir`** — `createSettingsStore` throws
  `QWAUDIO_GATEWAY_CONFIG_DIR_REQUIRED` without one, so an embedding host cannot accidentally share
  the standalone app's data directory (`desktop/src/settings-store.mjs`).
- **Every store accepts `filePath = null`**, in which case it runs **memory-only**. This is how
  tests and ephemeral hosts avoid touching the filesystem, and it means `filePath` being unset is a
  supported mode rather than a misconfiguration.
