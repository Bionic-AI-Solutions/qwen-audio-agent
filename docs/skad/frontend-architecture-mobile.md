## The single most important fact about this part

**The mobile app is not a second UI. It is a pairing shell around the web app.**

`mobile/src/main.jsx` renders an onboarding screen until a Gateway profile exists, then
**dynamically imports the web client** and mounts it:

```js
const module = await import('../../web/src/App.jsx')
setWebApp(() => module.default)
```

It also imports `web/src/gateway-transport.js` and `web/src/styles.css` directly across the
workspace boundary. Consequences to keep in mind when editing:

- **Any change to `web/src/App.jsx` ships to mobile.** There is no mobile fork and no abstraction
  layer between them.
- The web app is loaded as a **lazy chunk**, so it is absent from the initial bundle and only
  fetched after successful pairing.
- Mobile differentiates itself purely through `configureGatewayTransport({ clientType: 'mobile' })`
  and `mobile.css`. Behavior differences are negotiated by **capability**, not by branching on
  platform — e.g. `voice-defaults.js#initialVoiceEnabled` turns voice on automatically when
  `clientType === 'mobile'`.

## API surface

The mobile part exposes no API. It consumes exactly **one HTTP endpoint directly**; everything else
happens through the embedded web client's transport (see
[`api-contracts-web.md`](./api-contracts-web.md)).

| Method | Endpoint | Call site | Purpose |
| --- | --- | --- | --- |
| POST | `<gateway-origin>/api/access/pair` | `mobile-profile.js#pairMobileGateway` | Redeem a pairing code for a device access token |

Request body: `{ code: <pairing_code>, device: { id, type: 'mobile', label } }`.
Response consumed: `access_token`, `device.id`.

It is issued via `CapacitorHttp.post` (native HTTP, bypassing the WebView) with **10 s connect and
read timeouts**, not `fetch`.

## Security model — HTTPS is mandatory, twice

This is enforced in two independent places, and both must stay:

1. **At pairing** (`pairMobileGateway`): if the decoded invitation's `gateway_url` is not `https:`,
   it throws with `code = 'mobile_gateway_requires_https'` before any request is made.
2. **At profile load** (`parseMobileGatewayProfile`): a stored profile is rejected — returns `null`,
   forcing re-pairing — unless `url.protocol === 'https:'` **and** `url.origin === gatewayUrl`
   (i.e. the stored value is a bare origin with no path, query, or fragment). A profile missing
   `accessToken`, `deviceId`, or `clientInstanceId` is likewise rejected.

The error message names the intended deployment: Tailscale-provided HTTPS to reach a Gateway
running on the user's own machine.

`capacitor.config.json` reinforces this at the platform level with `iosScheme` and `androidScheme`
both set to `https` under hostname `qwaudio.local`.

## State management

No state library, and far less state than the web part — because the web app takes over once paired.

### `MobileApp` component state (5 hooks)

| Hook | Purpose |
| --- | --- |
| `profile` | The validated `MobileGatewayProfile`, or `null` when unpaired |
| `WebApp` | The lazily-imported `web/src/App.jsx` default export |
| `invitation` | Textarea contents for manual `qwaudio://connect…` link entry |
| `status` | User-facing status line (`role="status"`) |
| `busy` | Disables the scan/connect buttons during an in-flight operation |
| `pairing` (ref) | **Re-entrancy guard** — prevents a concurrent second pairing when a QR scan and a deep link fire together |

The `pairing` ref is deliberate: `pair()` can be triggered by three independent sources (launch URL,
`appUrlOpen` listener, barcode scan), and without the guard two would race to write the profile.

### Persistence — two stores with different guarantees

| Data | Store | Key | Rationale |
| --- | --- | --- | --- |
| Gateway profile (**contains `accessToken`**) | `@aparajita/capacitor-secure-storage` | `mobile-gateway-profile` | Keychain / Android Keystore — credentials never touch `Preferences` |
| Device ID | `@capacitor/preferences` | `mobile-device-id` | Non-secret, must survive so re-pairing reuses the same device identity |

Splitting these is intentional. Moving the profile into `Preferences` would put a Gateway access
token in plaintext app storage.

`mobileDeviceId()` is lazily generated as `mobile_<uuid>` on first call and then stable for the
install — this is what makes per-device token revocation on the Gateway meaningful.

## Native integration (Capacitor 8.5.1)

| Plugin | Version | Used for |
| --- | --- | --- |
| `@capacitor/core` (`CapacitorHttp`) | 8.5.1 | Native HTTP for pairing; enabled in `capacitor.config.json` |
| `@aparajita/capacitor-secure-storage` | 8.0.0 | Keychain/Keystore profile storage |
| `@capacitor/preferences` | 8.0.1 | Device ID |
| `@capacitor/barcode-scanner` | 3.1.2 | QR pairing (`QR_CODE` hint, back camera, adaptive orientation) |
| `@capacitor/app` | 8.1.1 | `getLaunchUrl()` and `appUrlOpen` for `qwaudio://connect` deep links |

`onMobileUrlOpen` returns a disposer and handles the case where the component unmounts before
`addListener` resolves (`disposed` flag → immediate `.remove()`), avoiding a leaked listener.

### Three entry paths into pairing

1. **Cold start with a stored profile** → `loadMobileGatewayProfile()` → activate directly.
2. **Cold start from a deep link** → `mobileLaunchUrl()` → `pair(url)`.
3. **Running app receives a deep link** → `appUrlOpen` listener → `pair(url)`.
4. **Manual** → QR scan or pasted invitation link.

## UI components

| Component | File | Category | Notes |
| --- | --- | --- | --- |
| `MobileApp` | `main.jsx` | Root | The entire mobile-specific UI |
| `<WebApp/>` | dynamic import of `web/src/App.jsx` | Root | The real application, mounted post-pairing |

The onboarding screen is plain semantic JSX — `<main>`, `<h1>`, `<button>`, `<textarea>`,
`<small role="status">` — with class names from `mobile.css`. There is no component library. A
`mobile-disconnect` button overlays the embedded web app to clear the profile.

**All user-facing strings are Simplified Chinese literals**, consistent with the `i18n.js`
convention where Chinese text is the translation key.
